Reproduction and exact fixes

P1 B01 · Confirmed

Opening a draft can silently switch its play

All plays · Open draft → Build → SOW

What goes wrong / reproduction

Save a CJA draft with a customer and six-month term. In another browser context, choose AEM, enter its SOW, and open that CJA JSON. The SOW initially shows CJA correctly. Click Build: the canvas still shows AEM. Continue back: the draft becomes AEM with twelve AEM services, while retaining the CJA customer and six-month term. No change-play confirmation appears.

Exact fix

Save a versioned canvas snapshot with the draft: play ID, product IDs, service choices, replacement choices, size, rate and term. On import, validate and restore both SOW and canvas state together, reconcile selections from the imported estimates, and clear stale handoff data. For old named-play drafts, reconstruct the canvas from the imported play and saved selections. For old custom drafts, recover only verified product IDs and require review of anything unrecoverable; never retain a different previous canvas. Handle an empty browser with no canvas key too.

Code location and retest

site/sow/index.html: syncCanvas() (282–286), Save/Open draft (451–453), applyHandoff() (465). Saved SOW state lacks a durable custom-product-ID snapshot.

Acceptance test: Cross-play import, empty-browser import and custom drafts with different product sets must retain the imported engagement through Build → Services → export. Current v4 JSON preservation alone does not prove this journey works.

P1 B02 · Confirmed

SOW-added catalog services disappear through Build

Brand Visibility alone · L03; also other catalog additions absent from the canvas

What goes wrong / reproduction

In the Brand Visibility play, go to Services → Add service → Automated optimization deployment pilot (L03). Return to Build, then Services. L03 is silently deselected. Its Typical 40 hours / $6,000 one-time test fee disappears. The same ownership gap affects X01 workshops and other catalog additions whose owning product/connection is absent; partner-created CUSTOM lines are exempt.

Exact fix

Include an explicit managed-service-ID set in the canvas handoff. Update on/off only for IDs that canvas owns; preserve selected SOW-only IDs that are absent from that set. For actual product removal, send an explicit removal list. Retain SOW-only services in the shared state and show them in a retained-services summary so the canvas cannot imply they were removed or omit their fees silently.

Code location and retest

Canvas site/index.html: handoff 617–619 sends only current products/connections. SOW: syncCanvas() 285 stores the flag, but applyHandoff() 476–477 treats every absent non-custom line as off.

Acceptance test: Add L03 in ABV and X01 in each named play; edit scope; round-trip, reload and Save/Open. Keep selection and edits. An explicit removal must still persist.

P1 B03 · Confirmed

A withdrawn rate comes back

All plays · Build hourly rate → SOW

What goes wrong / reproduction

On CJA enter 150, continue to SOW, return to Build, clear the hourly rate and continue again. The SOW restores 150 and writes it back into the canvas. Clearing a commercial input must not reactivate its previous value.

Exact fix

Distinguish a missing handoff property from an explicit blank. If rate is present and blank/null, set state.rate = ''; otherwise normalize its value with the existing amount helper. Keep legacy “property omitted” behavior separate. Preserve independent line-rate overrides. A cleared global rate should remain blank/unpriced under the tool’s existing behavior.

Code location and retest

Canvas handoff at 619 serializes rate: st.rate || ''; SOW applyHandoff() at 468 ignores the explicit blank. save()/syncCanvas() then reintroduces the old rate.

Acceptance test: 150 → blank → SOW → Build remains blank; blank → positive carries through; line-rate overrides survive a global-rate clear.

P2 B04 · Confirmed

Canvas totals ignore effective service bands and overrides

Brand Visibility example · Scope coverage, Services, Build total

What goes wrong / reproduction

With the default ABV play and rate 150, enter 100 tracked prompts on Scope. The SOW correctly moves L01/L02/O01 to Small and totals $175,200. Build still uses global Typical hours and shows $210,000. Returning to SOW restores $175,200. No hours were typed manually. In a second case, O02 Small + line rate 175 + one-time cadence yields $101,800 in SOW and $210,000 on Build.

Exact fix

Render Build’s estimate using the effective per-service band, including prompt-derived bands, plus per-line rates and cadence from the saved engagement. Reuse the effective-line calculation rather than calculating every line from st.size, the global rate and catalog cadence. If Build intentionally remains a baseline-only estimate, explicitly label it as such and display the current SOW estimate separately; do not show the conflicting numbers as one engagement total. Preserve the documented treatment of manually typed hours unless separately changed.

Code location and retest

Canvas hrs()/fee()/totals() around 228–252 use global size/rate and native unit; SOW syncBands() 440–441 resolves coverage and individual bands. This extends beyond UNRESOLVED item 19’s acknowledged typed-hour and currency differences.

Acceptance test: 100 prompts with Typical global size must reconcile or clearly distinguish the two estimates. Also check an individual Small band, line-rate override and cadence change independently. Returning must retain all edits.

P1 B05 · Confirmed

A band change exports stale acceptance criteria

Coworker · CW01 workflow discovery · Services → HTML and CSV

What goes wrong / reproduction

Choose CW01 Large using its card dropdown, then download immediately. Scope promises four workflows at 32 hours; acceptance still says “both workflows.” Both actual HTML and CSV downloads contain the contradiction. Reload repairs it to “all four.” Small has the corresponding two-versus-one error.

Exact fix

Use one band-application helper for dropdown changes, matched-hour changes, global size changes and draft load. Reconcile all five unedited fields together: scope, deliverable, acceptance, assumptions and exclusions. Preserve genuine partner edits. At minimum the dropdown handler must refresh acceptance; the shared helper prevents the same divergence elsewhere.

Code location and retest

site/sow/index.html: card-band change at 433 updates scope/deliverable only; syncBands() at 440–441 updates all five. Verified in actual downloaded cw01-large.html and cw01-large.csv.

Acceptance test: Typical → Large and Typical → Small: preview, saved draft, HTML and CSV must agree before and after reload.

P2 B06 · Confirmed

Large Brand Concierge has conflicting handoff counts

Financial services · F02 Implement Brand Concierge · Large band and SOW

What goes wrong / reproduction

The Large estimate basis promises two handoff routes. Included work still specifies one supported handoff. Both appear in the same downloaded SOW. Unlike B05, reload does not repair this: the catalog’s Large quantity has no matching scope override.

Exact fix

Add a Large-band F02 scope override replacing the one-handoff clause with “set up two separately agreed, supported handoff routes to the customer-designated teams.” Align deliverable and acceptance so each route is named and tested. Keep the existing hours and existing Adobe-confirmation condition for unsupported destinations. If the intended commercial scope is only one route, correct the quantity instead; do not retain conflicting counts.

Code location and retest

F02 in site/sow/index.html CATALOG at 41; band fallback around 204. Actual downloaded f02-large.html contains both counts.

Acceptance test: Small, Typical and Large must have matching quantity, included-work, deliverable and acceptance counts in preview and both exports.

P1 B07 · Confirmed

Supported legacy drafts lose multiplied hours and fees

Coworker reproduction · v2/v3 draft import · CW01

What goes wrong / reproduction

A controlled version-3 fixture has CW01 Typical 20 hours, quantity 2, unchanged scope and hoursEdited=false. Open draft accepts it. Expected 40 hours at the test override £199.99 = £7,999.60; actual import and downloaded HTML/CSV show 20 hours and £3,999.80. The quantity-two note disappears and no migration review is requested. This is a constructed compatibility fixture, not a claim about a supplied customer draft.

Exact fix

Reconcile old text first, then migrate quantity. Preserve multiplied hours as an explicit migrated override, retain the original unit count, and require meaningful reconciliation before issue. Do not let syncBands() reset imported quantities to a single planning band. Apply the same rule to browser-state restoration. This preserves old contracted scope without changing catalog hours.

Code location and retest

SOW normalization 251 multiplies and appends a note; text reconciliation 254–256 overwrites the note; Open draft 453 calls syncBands(), which resets hours because hoursEdited stayed false.

Acceptance test: Test v2/v3 quantity 0, 1 and 2, unchanged defaults and edited text. Check hours, scope note, fees, Save/Open and both downloads.

P2 D01 · Confirmed

Old SEO scope can return beside SO2 without overlap review

AEM · legacy O03 → CUSTOM-O03-aem plus SO2

What goes wrong / reproduction

Intentional migration correctly preserves old O03 as a custom service. However, the unchanged old technical-SEO scope remains selected beside SO2, and issue validation reports no overlap. Both can cover the same site’s metadata/schema/redirect fixes. The test draft adds 56 hours/month ($8,400 at test rate 150), taking the annual total from $484,800 to $585,600. That $100,800 is unreviewed additional scope, not a proven entire overcharge.

Exact fix

Keep the old custom line, its selection, text, hours and rate. Persist a retiredFrom: 'O03' marker through normalization and serialization. When it coexists with SO2, require the partner to remove one line or name a distinct additional backlog/site/deliverable outside SO2 before issue. Inherited boilerplate is not a distinction. Save/Open must preserve the resolved review. Do not silently delete, deselect or zero old work.

Code location and retest

SOW normalization 221–259 and retired-line handling 268–269; overlap rules 315–317 and issue checks 341–343. Actual application functions in Chromium retain both lines and return issues() === [], including after a second normalization.

Acceptance test: Import an old selected O03 with SO2. Show the review; require a genuine distinct-scope explanation or explicit removal. Preserve both fees only after that choice.

P2 C01 · Confirmed

Sites Optimizer scope implies every fix is an authoring change

AEM · SO1 setup and SO2 monthly fixes · SOW assumptions

What goes wrong / reproduction

SO1/SO2 describe approved fixes as landing in authoring for people to publish, including manual implementation under Prime. That is too broad for the included Core Web Vitals work. Adobe documents code patches requiring a repository, developer review, testing and merge; relevant deployment features are Early Access. The canvas connection already has richer caveats that do not flow into these ordinary SOW lines.

Exact fix

Replace the universal authoring language with: “Deployment follows the selected opportunity and enabled route. Supported Ultimate content fixes go to source documents or authoring for review and publishing. Core Web Vitals fixes use code patches and the existing development workflow; a named developer reviews, tests, merges and releases them. Automated PR submission and Dispatcher redirects are included only where Adobe has enabled the relevant Early Access capability. Under Prime, approved recommendations are implemented manually through the appropriate content, code or configuration workflow.” Add the repository, permissions, reviewer and release owner as prerequisites; Core Web Vitals analysis needs eligible pages with at least 1,000 page views. In SO2’s scope, involve the developer for code/configuration changes. If code repair is not intended, explicitly exclude it instead of promising it as authoring work.

Code location and retest

SO1/SO2 in SOW CATALOG at 41, printed in section 3 at 125. Evidence: S1 code patches, S2 Core Web Vitals, S3 release notes. No change to hours or separate duplicate remediation package is needed.

Acceptance test: Generate the AEM SOW with SO1/SO2. A delivery lead must be able to identify content vs code routes, ownership and unavailable-feature exclusions directly from that document.

P2 C02 · Confirmed

CJA audience prerequisites allow a substitute the scope does not deliver

CJA · C06 Audiences that act on the data · SOW assumptions

What goes wrong / reproduction

Scope and acceptance promise publication into Real-Time Customer Profile. Assumptions instead allow “Real-Time Customer Profile or another supported destination.” A downstream destination is not a substitute for the Profile step that the SOW promises. Audience publishing permissions and the connection’s Person ID/namespace also need to be recorded.

Exact fix

Replace the opening assumption with: “The customer has the Adobe entitlements and enabled Real-Time Customer Profile service required to receive CJA audiences, the necessary audience-publishing and profile-management permissions, and an agreed Person ID and identity namespace in the CJA connection. Channel owners confirm identity, consent and intended activation use. Any downstream destination is already configured and licensed; it does not replace the Real-Time Customer Profile publishing step.” Retain the existing clarification that the ABV aggregate bot dataset is not the audience source. Do not require every source dataset to be Profile-enabled; Adobe expressly permits otherwise.

Code location and retest

C06 in SOW CATALOG at 41, printed in section 3. Evidence: S4 audience publishing overview and S5 publish audiences. C06 stays a starting service, as settled.

Acceptance test: Generate CJA SOW and check that scope, acceptance and prerequisites describe the same publication route and identify the required tenant capability.

Smaller corrections and evidence precision

CSV currency rounding

All plays; reproduced on Coworker. Fractional hours/rates produced a raw CSV term total 49175.104999999996; the exact decimal work value is 49175.105 and the SOW displays £49,175.10. Another tested total was 52199.630000000005. Integer baseline calculations reconciled; this is precision/policy consistency, not evidence of a large arithmetic error.

Fix: define whether totals sum rounded line fees or unrounded work values, define half-cent handling, use decimal/minor-unit calculations, and export all currency columns at currency precision. Use the same calculation in cards, document and CSV. Check selectedLines(), totals() and CSV serialization in site/sow/index.html.

L03: add the content-opportunity preflight

Any play selecting the deployment pilot; C07 when it owns routing. General route eligibility is stated, but the applicable source-header check is missing. Adobe skips relevant content optimizations when the source response lacks a valid Last-Modified header. This is a missing preflight detail, not proof the entire pilot is unsupported. [S6]

Exact addition: “For content opportunities that monitor source changes, verify a valid Last-Modified response header on the selected source pages before deployment. Adobe skips the optimization if it is absent. The existing routing/deployment owner performs this check; agree any remediation before the pilot.” Assign that work once between L03 and C07.

C03: remove an unsupported absolute about AEM handoff

AEM optimization publishing workflow. “Adobe documents no direct publishing link” is not established by the cited edge-deployment page. Adobe’s current product page describes sending recommendations to AEM Sites. That marketing statement also does not prove a turnkey API or automatic production publish for every tenant. [S7]

Exact replacement: “This service scopes the customer’s recommendation-to-review-and-publish workflow. Confirm the tenant’s available Brand Visibility-to-AEM recommendation handoff before implementation; use the supported native route where enabled, otherwise an agreed partner-managed authoring handoff. Production publishing remains subject to the customer’s review and approval process.”

F02: cite the detailed current documentation

Brand Concierge implementation. The general product documentation is a genuine reference, but its older introductory text is less useful than the current detailed pages for handoff and rollout. The SOW’s Qualifier route, 30-day retention and example gradual rollout are supported; do not remove them just because a broad homepage is stale.

Fix: put the current handoff overview [S8] and pre-go-live guide [S9] next to the claims. Preserve the distinction that ordinary chat/meeting handoff does not itself require Marketo Engage; custom routing/Marketo activity recording can.
