Retired O03 migration changes the fee basis

AEM reproduction; applies to any saved play with O03 · Open draft → Services → HTML/CSV

Exact steps

Open a supported version-4 draft with selected O03 at 56 hours, one-time cadence, rate 150 and twelve months. Turn SO2 off in the fixture to isolate the import from its separate overlap check. Complete ordinary commercial terms. Inspect the migrated CUSTOM-O03-aem and download the SOW and CSV. A second fixture uses version 3, 56 hours, quantity two and monthly cadence.

What goes wrong and partner impact

The one-time line becomes monthly: $8,400 one-time becomes $100,800 across twelve months, a $92,400 increase caused solely by migration. The quantity-two case imports 56 rather than 112 hours, halves its term fee from $201,600 to $100,800 and loses the quantity-review note. Both actual downloads succeed; issue validation is empty. These are controlled fixtures using accepted legacy formats, not assertions about a supplied customer’s draft.

High for affected imported drafts. A commercial document can silently gain recurring charges or lose contracted units. The prior active-service quantity fix and the O03/SO2 overlap check both work; this retired-service migration bypasses the common path.

Exact fix

Migrate the complete original O03 estimate before renaming it. Preserve cadence, selection, rate, hours, all edited text and relevant reasons/flags. Apply the common v2/v3 quantity conversion exactly once, with its review note. Pass that transformed row through normal normalization under the replacement custom ID. Keep retiredFrom:O03 and the existing SO2 distinct-scope check. Do not reconstruct the line from only on/rate/base and a hard-coded monthly unit, and do not silently remove or zero it.

Source location, evidence and retest

site/sow/index.html:237–239 creates the replacement with unit:'monthly' and only part of the old row. Lines 252–264 look for the new ID in the old estimates, so ordinary cadence/quantity migration is skipped. Line 266 restores unmultiplied base hours.

Evidence: Actual o03-one-time.html/.csv and o03-qty2.html/.csv; exports-legacy-o03-results.json. The one-time migration was independently repeated by the lead reviewer.

Acceptance test: Import v2/v3 quantities 0, 1 and 2; one-time and monthly cadence; explicit line rates; SO2 on and off. Compare hours, cadence and fees before/after migration, Save/Open and both downloads. Apply quantity review and overlap review independently when relevant.

P2 F2 · Confirmed

Canvas Start over can resurrect a legacy customer and terms

Any play · Build Start over → new play → Scope; legacy-browser upgrade path

Exact steps

Seed an accepted v3 engagement only under the legacy local-storage key partner-services-focused-v2, with no partner-sow-studio-v6 key. Use a previous customer/partner, nine months and substantive old commercial terms. Open Build without visiting SOW first; choose CJA, enter rate 150, use Start over and confirm. Pick Brand Visibility alone and continue.

What goes wrong and partner impact

Build initially resets to twelve months, but SOW loads the untouched legacy key. The previous customer, partner, commercial terms and nine-month duration reappear in the new ABV engagement. Its total is $163,200 instead of the fresh twelve-month $210,000 at the test inputs. No warning identifies the restored commercial fields.

Moderate and narrowly triggered, but explicit reset must discard the previous engagement. This differs from README’s accepted temporary old-state total mismatch: old customer and terms return after the user deliberately clears them.

Exact fix

Add partner-services-focused-v2 to the canvas Start over clear operation, alongside the current SOW key and handoff. Keep the approved rate and size in canvas state. Use one shared list of engagement storage keys for reset/migration. Do not apply this clearing to ordinary Change play, which intentionally preserves Scope details.

Source location, evidence and retest

site/index.html:650 clears the current SOW and handoff keys but omits the old key. site/sow/index.html:174,283 declares/loads that legacy fallback; line 295 removes it only after it has already been read.

Evidence: test-state-legacy-reset.cjs and state-legacy-reset-results.json, rerun with actual totals. Fixture values are test-only.

Acceptance test: Seed only the legacy key, perform the real Start over flow and select another play. The next SOW must have blank customer/partner/terms, twelve months and the retained rate/size. Repeat after the browser has already migrated to current storage.

P2 F3 · Confirmed

Change play leaves edits on partner-created services

CJA reproduction; any play with an own service · Change play → reselect → Add service

Exact steps

Create a partner workshop defined as 20 hours, one-time, with one workshop and an outcome document. Edit its service row to 99 hours, rate 250, monthly cadence and a different nine-workshop scope. Build → Change play → confirm that choices and edits will clear → select CJA again. On Services, add the workshop again from the service library.

What goes wrong and partner impact

The service correctly turns off during reset, but the later row edits survive. Add service previews the original 20-hour one-time definition; adding it restores 99 hours/month at 250 and the superseded scope. At the test inputs the engagement becomes $516,600 instead of adding the original $3,000 workshop to the $219,600 baseline.

Moderate. Re-adding is an explicit user action, so this is not an automatic hidden charge. It still contradicts the confirmed reset semantics and can revive a previous engagement’s commercial overrides.

Exact fix

Keep state.custom, the reusable original definitions. During the fresh-play reset, replace each affected custom estimate with newLine(customService, false, state.size, play) instead of only setting on=false. This resets row edits, reasons, line rate and cadence while retaining the definition under Add service. Leave normal Remove → Add behavior unchanged if it intentionally restores edits.

Source location, evidence and retest

site/sow/index.html, applyHandoff() fresh-play branch around 515–521: non-CUSTOM estimates are rebuilt, but CUSTOM rows are only deselected. The canvas Change play dialog around line 645 promises all edits are cleared.

Evidence: custom-own-reset-results.json. Independently repeated on ABV with a 12-hour original workshop changed to 40 hours/month at 300.

Acceptance test: Edit all five contract fields, hours, reason, line rate and cadence on an own service. Change play, reselect and re-add. Restore the original definition with inherited global rate and no old override. Separately verify that the reusable definition itself survives.

P2 F4 · Confirmed

A03 Large includes and excludes the same support weeks

AEM + Sites Optimizer + EDS · A03 Launch, QA and hypercare · Large band

Exact steps

Select the AEM play. Set A03 to Large, or choose Large delivery size. Read Included work and Excluded work, complete ordinary commercial terms and download the SOW. Repeat with Small.

What goes wrong and partner impact

Large includes four weeks after launch, but Excluded work excludes support beyond two weeks of hypercare. Weeks three and four are simultaneously included and excluded. Small includes one week but inherits the same two-week exclusion. Typical is consistent. Actual HTML downloads contain the contradiction and can issue.

Moderate: a customer-facing support obligation is ambiguous. This is an internal SOW scope contradiction, not a double charge or an Adobe capability overclaim.

Exact fix

Replace the shared exclusion with: “New features, content changes after launch, and support beyond the hypercare period stated in Included work.” Keep the existing one/two/four-week scopes and all hours. Add the old default to the known-text migration list so untouched drafts update while genuine partner edits survive.

Source location, evidence and retest

A03 in site/sow/index.html:41; lineText() around 203; migration around 259–260. Adding only bands.large.exclusions will not work: lineText currently applies band overrides only to scope, deliverable and acceptance. The duration-neutral base exclusion is the smallest fix.

Evidence: Actual a03-large.html and a03-small.html; exports-adversarial-results.json. Static identification and independent download confirmation agree.

Acceptance test: Check Small/Typical/Large in preview, HTML, CSV and Save/Open. Test an unchanged older exclusion and a partner-edited exclusion separately.

P3 F5 · Confirmed

Delivery-size help text overflows the mobile Services page

All plays · Services estimate controls · reproduced at 390 CSS pixels wide

Exact steps

Open ABV, go to Services and view at 390px width. Inspect the help text beneath Delivery size and try horizontal scrolling.

What goes wrong and partner impact

The document expands to 424px because the help text inherits white-space:nowrap. Its right edge extends beyond the viewport. Controls remain usable; this is a small readability/layout defect.

Low. It matters on phones and narrow windows, not the normal desktop partner walkthrough.

Exact fix

At the mobile breakpoint, allow help text to wrap and let its flex item shrink:

@media (max-width:780px) {
  .estimate-strip small { white-space:normal; }
  .size-field { min-width:0; max-width:100%; }
}
A temporary browser-only application of this CSS reduced measured document width from 424px to 390px. Packaged source was not changed.

Source location, evidence and retest

site/sow/index.html stylesheet: .estimate-strip small and .size-field.

Evidence: mobile-overflow.json, readability-results.json and the isolated CSS measurement. Screenshots were used internally for inspection.

Acceptance test: Services at 390px and 360px: no page-wide horizontal scroll, fully readable help text, all size buttons reachable. Recheck desktop wrapping.

My recommendation on Download template

Remove it from the partner-facing menu for this release. It exports only the SOW half of a two-page builder, so its offline navigation does not fulfill the implied promise. Keep Save draft, Download SOW and CSV. Bring back an offline builder only when both pages and their state/navigation work together, or the exported page is independently functional. This is the owner decision explicitly requested in README, not a newly discovered bug. Nothing was removed during this review.

Low-priority numeric boundary observation

Entering a global rate of 0.004 rounds to numeric zero after the positivity check. Services temporarily treats it as supplied while Build treats zero as no rate; a trip normalizes it. This is not a realistic approved partner rate and is not a release blocker. The small fix is to round first, then apply the positive-global-rate rule, while preserving intentional zero line-rate overrides. It does not change the successful two-decimal money checks.
