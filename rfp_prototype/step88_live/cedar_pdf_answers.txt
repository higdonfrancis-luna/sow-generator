### B.3 Describe how you would make the new site conform to WCAG 2.2 Level AA, and how accessibility would be checked before each release.
[claude-opus-5-5; A01, A02]

Our approach
- With 900 PDFs including state rate filings, we build accessibility into the blocks and templates your authors use, not each author's habits.

How we would do it
- Set WCAG 2.2 Level AA acceptance criteria for each block and template: contrast, focus, target size, headings and labels.
- Build semantic, keyboard-ready blocks, tested with screen readers on the Edge Delivery preview URL.
- Run automated accessibility and Lighthouse checks on every change in the GitHub repository; a failing change is not deployed.
- Check headings and alternative text on migrated pages, and inventory the PDFs to remediate priority documents.

What you get
- Acceptance criteria, an accessible block library and templates, automated checks, a PDF inventory and release accessibility reports.

Timeline and effort
- This work runs within the ten-month launch. The planning estimate is 1,200 hours across site build and migration. PDF remediation is sized once the inventory is agreed.

Risk we manage
- Later edits can break conformance, so templates enforce structure and every release is checked.

What you get

Timeline and effort
- Ready before migrated content enters authoring, inside your ten-month launch. Planning estimate: 200 hours.

Risk we manage
- Unapproved regulated pages going live; we handle it with the intake flag and a release check against approval records.
