Part 2

The front end is the easy part now

Screens, buttons, layout and wording are what you see, and that part is now a conversation. Describe what you want to Claude or ChatGPT, ask for a picture, react to it, and it gets built. I never wrote a line of HTML by hand.

What still takes real thought is everything behind the screen: where the code lives, where the data comes from, where the site runs, and how an AI feature calls a model without exposing a key. That is the rest of this page.

Part 3

The back end, in plain terms

Four systems carry the tool from a conversation to a partner's screen. A fifth is optional.

Claude or ChatGPTThe conversation. Writes the code and the research.
GitHubWhere the code, the data and every past version live.
HostingNetlify first, now Adobe Proto. Serves the site.
Partner's browserRuns the whole tool. Nothing typed leaves it.

Optional: Cloudflare Worker. Only for the AI buttons in the RFI Builder ("Read with AI" and the AI-written proposal). The browser asks the Worker, the Worker asks a Claude model on AWS Bedrock. The core tool works without it.

GitHub

The memory
What it is

An online home for code. Every change is saved as a "commit" with a one-line note, so any version can be seen or brought back.

Why I use it

AI chats forget. GitHub doesn't. Every session starts by reading the project from GitHub and ends by saving to it, so nothing is lost between conversations.

It is also how two AIs share one project: Claude writes a brief, ChatGPT builds on its own branch, and Claude reviews and merges the work.

How the AI connects

Claude Code: sign in to GitHub from Claude and install the Claude GitHub app on the repository. Each session copies the repo, works, and pushes to its own branch.

ChatGPT: connect GitHub in ChatGPT's connectors (Codex works directly in the repo).

The data

No database
What it is

Three files in GitHub: the catalog (34 Adobe products, 151 connections, 531 services with hours), the facts (security, hosting, licensing) and the methods (how each service is delivered).

Where it came from

AI research agents read Adobe's public documentation, mostly Experience League, product by product. Every service was saved with its page and a quote. No source, no service: 723 Adobe pages in all.

Why files, not a database

Private, because it all runs in the partner's browser. Free. Works offline. And every data change is a GitHub commit, which is the audit trail. A small Python script checks the files and builds them into the page.

Hosting: Netlify, then Adobe Proto

The address
What it is

The service that puts the files at a web address. The tool is just files, so any simple host works.

Why these two

Netlify was first (abvsow.netlify.app): a public link, published in one step. Adobe Proto (proto.adobe.io/sow-generator) is home now: an Adobe login, inside Adobe.

How the AI connects

Netlify: Claude publishes through the Netlify connector when I say "deploy", and every release can be rolled back.

Proto: no AI access. Claude builds a zip and I upload it by hand.

Cloudflare Worker

The key holder
What it is

A small program that runs on Cloudflare's servers: a tiny back end. Mine is called warroom-assistant and it also serves WARROOM.

Why I need it

A web page can't keep a secret: anyone can read its code. AI models need a paid key. So the key lives on the Worker as a locked secret, the page calls the Worker, and the Worker calls the model. The key never reaches a browser.

How the AI connects

Claude reads and updates the Worker's code through the Cloudflare connector, or the Cloudflare API with a token saved in Claude's environment settings. It deploys only after I say yes, then tests a route.

Secrets are set once in Cloudflare and can't be read back out, by me or by Claude.

Part 4

How Claude and ChatGPT reach these systems

This is the part that sounds technical and isn't. There are three ways in, and you set each up once.

Connectors

A built-in plug between the AI and an app such as GitHub, Cloudflare or Netlify. You sign in and approve it once; after that you just ask ("publish it", "show me the Worker code").

A saved token

Where no connector exists, the app gives you a key (a token). Save it in the AI tool's environment settings, never in the chat. The AI uses it without ever showing it.

By hand

Some places, like Adobe Proto, don't let an AI in. The AI prepares the file; you do the upload. That's fine.

  • Never paste a key into a chat. Use a connector or the environment settings.
  • Never put a key in GitHub. Keys live on the Worker or in settings.
  • The AI asks before anything goes live. Saving to GitHub is routine; publishing waits for a yes.
  • Change your keys before sharing a project. Assume an old key has been seen.

Part 5

If you want to build one

  1. Start with a conversation. Describe the problem and who it is for, then say "what if" as often as you like.
  2. Ask for a picture before any code, and say yes only to what you'd show a customer.
  3. Put it in GitHub from day one, so every session picks up where the last one stopped.
  4. Write your rules down once (mine: work and hours only, the partner's own rate, a source for every fact) and make the AI follow them.
  5. Ask for tests. Every fix should leave a check behind so the bug can't quietly come back.
  6. Need AI inside your tool? Put the key on a Cloudflare Worker, never in the page.
